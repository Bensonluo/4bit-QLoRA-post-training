# 任务规约与 Agent 全流程协作架构

2026-09-28 定稿（恢复循环第 58 轮）。北极星（`north-star.md`）定义产品目标与优先级，是目标权威；本文定义达到该目标的协作机制架构——任务规约的形态、Agent 在闭环各环节的职责边界、多轮适配的状态机。单点能力已齐备（见第 8 节证据），此前缺的是把它们讲清楚的整体架构：协作方式一轮一议，每个新环节都要重新论证"Agent 能不能碰、碰了谁兜底"。

---

## 1. 架构的第一性问题

北极星核心难点重述：每个场景都存在几处"答案只在业务方头脑里、数据本身推不出来"的语义判断。这些判断只能交给不可靠的 LLM（Agent）和不懂 ML 的用户，中间没有专家仲裁；判断错一处，后续工程全部白做且错误无声通过。

因此本架构的第一性问题不是"Agent 还能做什么"，而是**语义判断如何安全地传递**：LLM 的每次判断要么被确定性代码约束在可验证的形状里，要么被转化为用户做得起的核验动作，要么诚实失败。能力堆叠不解决安全问题，分层与边界才解决。

## 2. 三层架构

```
用户决策层   页面 + CLI（同源同词汇，stdout JSON / stderr 人话双流）
    │  显式确认动作 = 状态转移的唯一入口
Agent 建议层  src/agent/*：起草、核查、建议；产物一律停在待确认
    │  pydantic Contract 解析，失败即失败，不猜测修复
确定性内核   src/workbench/* 30 余个服务：唯一事实来源、
    │  确定性门禁、状态机、版本与血缘
```

- **确定性内核（单一事实来源）**：会话（IntakeService）、训练记录（TrainingRunService）、方案（TrainingPlanService）、对照报告（BusinessEvaluationService）、评分规则（ScoringService）、验收（AcceptanceService）、改进轮次（IterationService）、题集（EvalSuiteService）、自动执行（IterationExecutionService）。所有读写经服务层；结构上可验证的事实（泄漏、格式、截断、血缘、时间顺序）全部由代码判定，不依赖 LLM 或用户自觉。
- **Agent 建议层（起草-验证-待确认）**：五个入口——`analyze_intake`（数据分析与方案起草）、`recommend_training`（训练方案推荐）、`recommend_scoring`（评分规则拟定）、`assess_evaluation`（评测解读）、`revise_data_for_iteration`（按确认方向修订数据方案）。共同契约：输出用 Contract 结构化解析，解析失败直接报错，不做模糊修复；可用的核查工具只读（如 `read_cell_content` 分页读取长单元格），需要执行代码的场合（受限适配、评分规则验证）一律进入操作系统隔离环境，验证不过关不能确认。
- **用户决策层（页面与 CLI 平权）**：confirm / full-confirm / scoring-confirm / plan-prepare / train-start / acceptance-run / iteration-decide 等状态转移只能由用户显式动作触发。页面与 CLI 读同一批服务、同一批人话摘要函数（`report_summary` / `cost_lines` / `loss_trend_lines` 单一来源），两侧不各说各话；CLI 侧 stdout 纯 JSON、stderr 人话，脚本与人读共用一条通道。

**边界红线**（与北极星硬边界一致）：Agent 不改监督答案、不删坏例、不替用户确认、不自动启动训练、不接触最终独立测试题（`eval-analyze` 拒绝最终测试报告是代码级门禁，不是约定）；密钥只走环境与会话（BYOK），业务数据发送需逐次显式授权。

## 3. 任务规约（Task Spec）

**问题**：一个数据任务的语义定义目前分散承载——业务目标与描述（create 时录入）、处理方案与分析结论（`analysis.recipe`）、评分口径（已确认 scoring 规则）、验收标准（冻结的 acceptance 条款）、改进假设（iteration 记录）。每条记录各自可追溯，但用户没有一处能读到"这轮训练到底在学什么、按什么算对、验收按什么标准"的完整一页；跨轮次对照时更是要从五个目录拼装。

**定义**：任务规约 = 业务目标 ＋ 答案语义（监督信号的业务定义与盲标核验结论）＋ 评分口径（默认严格匹配 / JSON 字段 / 已确认自定义规则）＋ 验收标准（冻结条款或未冻结状态）＋ 时间约束（时间预测任务的字段与窗口）。四到五要素，一个任务一份。

**架构决策（ADR-1）：规约是只读投影，不是新实体。** 规约由既有记录汇编生成（session + analysis + scoring + acceptance + 最新 iteration），不新增存储、不引入第二事实来源。理由：规约若独立存储，就会与来源记录出现双写不一致——这恰是本产品要消灭的"无声错误"形态；投影永远可由来源重建，来源变化投影自动跟随，`revision` 乐观锁天然覆盖它。代价是投影只反映已确认的事实，草稿态（如待确认评分规则）不进入规约——这是特性不是缺陷：规约回答"当前生效的是什么"，草稿在各自的确认入口可见。

**消费场景**：方案确认时（学的是什么）、训练启动前（这轮按什么口径学）、验收冻结时（按什么标准判）、每轮改进时（父轮规约 vs 本轮变更范围）——四处读的都是同一份投影。

## 4. 各环节协作协议

九环节旅程（北极星「交付的完整闭环」）中 Agent 的角色逐段不同——**Agent 介入是设计选择，不是默认**：

| 环节 | Agent 职责 | 确定性门禁（代码） | 用户确认点 |
|---|---|---|---|
| ①数据准备与分析 | `analyze_intake` 起草方案、多源关联、受限适配；工具核查证据行 | 全量验证硬拦（缺答案/冲突/重复表头）；sheet/合并/公式/隐藏/空行如实标注 | 真实预览确认 ＋ 对比核验（软门禁） |
| ②训练方案制定 | `recommend_training` 基于数据事实、本机条件、真实 tokenizer 预检推荐 | 文件完整性检查；方案绑定任务版本 | plan-prepare / train-prepare |
| ③训练前检查 | 无（可学性探针为确定性代码，证据非门禁） | 截断/答案保留/EOS 契约；盲标核验（硬门禁，不通过训练不开始） | 盲标作答提交 |
| ④启动训练 | 无 | 预检风险需显式知晓；显存不足技术恢复最多一次、保持业务参数 | train-start 授权 |
| ⑤训练后对照 | 无（评分是确定性代码） | 同题、同协议、基座/父轮/本轮；失败截断留在分母 | — |
| ⑥可视化与解读 | `assess_evaluation` 核查坏例证据，输出观察/待验证原因/建议 | 解读必须读取训练配置与检查；最终题拒收 | 解读只读，不执行 |
| ⑦自定义评分 | `recommend_scoring` 拟定规则＋真实正反例隔离验证 | 隔离验证不过关不能确认 | scoring-confirm |
| ⑧独立验收 | 无（最终题与坏例不进 Agent） | 题目暴露阻断、阈值冻结、最低题数 | acceptance-run / 逐题人工判断 |
| ⑨改进轮次 | `revise_data_for_iteration` 按已确认方向修订数据方案 | 原题不可改写；新预览仍走确认链 | iteration-confirm / decide |

三个"无 Agent"环节（③④⑧）是刻意的：训练与验收两端的判断全部确定性化或留给用户，LLM 只在中间两段（理解数据、解读结果）和两个受验证约束的起草场景（方案、评分、数据修订）出场。这是"每一次性专家判断要么编码进产品、要么转化为用户做得起的核验动作"在协作结构上的落法。

## 5. 多轮适配架构

改进轮次是同一任务内的状态机，跨轮不变量由确定性内核保证：

```
propose → confirmed → (revise → 重新确认链) → prepared → started
        → evaluated(三模型同题对照) → decided ∈ {adopt, continue, stop, insufficient_evidence}
```

- **固定题集**：提案冻结父轮开发题与独立测试题（EvalSuiteService）；后续轮次同题对照，题数不够时结论如实保留证据局限，`insufficient_evidence` 是合法决定。
- **三模型对照**：基座、父轮、本轮各用自己的模型证据；父轮 adapter 保留作对照，不作为续训起点——每轮从同一底座重新微调。
- **数据修订边界**：`revise_data_for_iteration` 生成的新预览仍走完整确认链（预览→全量→确认）；原题输入、答案不能改写、缺失或进训练集；新增独立业务对象进训练，同组资料留在原保留分区。
- **一次授权自动执行**：IterationExecutionService 把"物化→训练→对照"串成自动推进，暂停等待确认时点名需要哪个入口勾选继续；执行状态与训练状态都只读查询，不触发推进。
- **决策留痕**：决定四态＋业务理由必填；采用记录不自动部署——与验收、导出的边界句同口径。

## 6. 状态绑定与版本纪律

跨环节引用图：`session.revision`（乐观锁）→ `dataset.version`（分区版本）→ `run_id`（训练）→ `evaluation_id`（对照）→ `iteration_id`（轮次）→ `suite_id`（题集）；模型库版本经血缘旗标反查 run 与 dataset version（`registry_link` 双向）。

每个人机决策点都检查 revision（"任务已更新，请读取最新 revision 后重试"）——语义判断的确认必须针对它被做出时的那份事实，防止"看过 A 确认了 B"。数据或方案修订后，绑定其上的核验结论（对比核验、盲标核验）自动失效并要求重做，失效是特性。

## 7. 人话与证据纪律（跨层横切）

- 双流契约：CLI stdout 纯 JSON、stderr 人话；页面与 CLI 同一批摘要函数，同源同词汇。
- 诚实红线：运行成功/loss 下降/样例通过不写成业务效果达标；零分如实记录；证据不足是合法结论；估计值标注为估计值（成本账、探针、盲标下界同口径）。
- 证据可追溯：训练证据链（adapter、loss 序列、export_evidence）、评测逐条输入输出、解读的工具核查轨迹、每轮决定与理由。

## 8. 与现状的对照（2026-09-28）

**已在场**（证据指针）：三层分层已是事实——workbench 30 余个服务、agent 五个入口全部 Contract 解析、确认动作全部显式；语义安全层三关卡（对比/盲标/探针）与确定性门禁（全量验证、预检、题目暴露阻断、最终题拒收）在代码中；双流契约与同源同词汇由 `test_cli_summaries`/`test_readme_alignment` 钉死；多轮状态机与自动执行在 `iterations`/`iteration_execution`；固定题集、三模型对照、血缘双向在位。

**缺口**（按优先级）：

1. **任务规约投影——已实现（Phase 1 落地，2026-09-28）**：`task-spec-show SESSION`（CLI 双流）＋ 页面「📋 任务规约投影」折叠区已落地（`src/workbench/task_spec_projection.py`，纯读、零新状态；消费场景已落训练启动前对齐与训练启动决策点两处，后者见第 9 节 Phase 2 切片 A；口径由 `test_task_spec_projection`/`test_readme_alignment` 钉死）。
2. **Agent 判断的真实性证据不足**（北极星差距②）：自定义评分的真实 GLM 起草未验证；单次在线验证入口就绪但未尝试（密钥纪律）。
3. **协作轨迹呈现已统一（Phase 3 落地，2026-09-28）**：数据分析环节 analyze 尾行与页面「处理规则与工具记录」区以评测解读同一格式渲染工具核查轨迹（`summarize_tool_trace` 单一来源，评测解读侧输出不变）；留痕落盘覆盖五个 Agent 入口（intake/evaluation/revisions/training/scoring 都建 trace 且持久化）；修订/评分/方案三处已上同格式人话行（R62 落地，2026-09-28，`summarize_tool_trace` 单一来源：评分与方案由摘要函数自动追加轨迹行、CLI 与页面同源，修订由页面修订折叠区直接渲染）；训练运行记录也已补齐（R63 落地，2026-09-28）：方案执行时把方案 trace 快照进运行记录（`plan_trace` 键），`summarize_training_run` 以评测解读同一格式渲染轨迹行，不经方案的直接启动如实没有该行——协作轨迹在五个 Agent 入口＋训练运行全链路的「落盘＋人话行」至此齐备，差距 3 完全收口。
4. **BYOK 连接质量仅探针**：连接测试只验证工具调用协议，不预测业务分析质量（已如实声明，暂无进一步机制）。
