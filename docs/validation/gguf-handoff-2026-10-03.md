# GGUF 消费级模型交接迭代

日期：2026-10-03。基线：`73831e0`，起始工作树干净。目标继续依据 [北极星](../plans/north-star.md)：非算法团队应能带走真实训练产物与证据，在自己的消费级硬件上继续使用。上一轮已修复来源与导出内容核验，本轮处理交接格式和真实加载缺口。

## 复现与根因

旧 `export_to_gguf` 调用 `llama.cpp/convert.py --outtype q4_k_m`，当前官方转换器没有该脚本入口，也不接受该转换精度。更严重的是包装函数捕获子进程失败却正常返回，外层 CLI 可以把失败当成功。旧回归还明确要求“不抛异常”，因而原绿灯不能证明实际 GGUF 可用。

官方流程分为本地 HF → 浮点 GGUF → `llama-quantize` 两步，本轮固定并实际验证官方源码版本 `436f6f89e1e581249900b37a5b8a12a36a6d0912`：[转换器](https://github.com/ggml-org/llama.cpp/blob/436f6f89e1e581249900b37a5b8a12a36a6d0912/convert_hf_to_gguf.py)、[量化工具](https://github.com/ggml-org/llama.cpp/blob/436f6f89e1e581249900b37a5b8a12a36a6d0912/tools/quantize/README.md)。

## 产品路径

1. `python scripts/setup_gguf_tools.py` 在独立缓存中准备固定官方工具，编译并自测 CPU 量化器。它不下载模型、不修改 Python 环境；外来目录、版本变化、缺依赖与编译失败均拒绝假成功。
2. CLI 的 `train-export RUN --format gguf --llama-cpp-dir PATH --quantization q4_k_m`，以及成功训练记录下的页面「导出模型」按钮，共用同一实现。默认 HF 路径保留；刷新页面仅轻量盘点，不执行导出或哈希大权重。
3. 独立 GGUF 目录保存模型、`export_evidence.json`、`Modelfile` 和 `USAGE.md`。来源、格式、精度、工具及文件内容绑定；临时合并/转换后复核并原子发布，错误不能留下假完成目录，外来产物不能被覆盖。
4. 摘要给出 LM Studio 的保留原文件导入命令和 Ollama 创建命令。模型加载是消费工具的操作；工作台没有加入 serving 层。量化后的业务验证状态明确为 `not_run`。

页面导出当前同步执行并显示 spinner，没有后台进度与取消机制；实际大模型导出耗时需要后续继续验证。

## 确定性核验

| 核验对象 | 实现与限制 |
| --- | --- |
| 来源与交接文件 | 继续使用训练运行、会话、数据版本、配置、基座、adapter 和 manifest 的内容绑定；输出目录逐文件 SHA256 完整复核。历史 HF 回执仍兼容；不同格式或精度不能混用 |
| 工具身份 | 转换脚本、Python 包源码、量化器与共享库记录内容摘要，Python 和相关依赖记录版本；合并前后和实际转换工具身份一致。转换使用全新的临时 Python 缓存前缀，避免“记录新源码却执行旧 `.pyc`” |
| GGUF 结构 | 标准库有界读取 v2/v3 元数据与 tensor 表，检查截断、计数、偏移、数据边界和词表存在；不物化大词表。量化块内容和架构可加载性仍需独立运行验证 |
| 精度 | 同时检查 `general.file_type` 与实际 tensor 类型，不接受只改精度声明、权重仍全浮点的假量化 |
| tokenizer 与模板 | 从实际加载的 HF tokenizer 读取模板，防止配置与 Jinja 优先级冲突；核对模型词表数量、BOS/EOS/PAD 与添加标记行为。Qwen 的补齐词表与未启用 BOS 别名按实际行为处理；没有把配置声明当作完整词表逐项映射证明 |
| 用户输入协议 | 训练和评测使用完整原始 Alpaca 提示。`Modelfile` 直接使用传入的完整提示；`USAGE.md` 说明占位文本、无 Input 分支和聊天界面附加模板的差别。保存基座聊天模板不代表训练采用该模板 |

## 真实集成验证

[机器可核查记录](gguf-handoff-live-2026-10-03.json) 绑定所有输出内容摘要与真实命令。

- 已有 Qwen3-1.7B 训练产物完成真实合并与 Q4_K_M 转换：HF 权重 3,441,185,608 字节，GGUF 1,107,408,640 字节。元数据为 `qwen3`、151936 个词表项、310 个 tensor；源 tokenizer 实际 151669 个 token，其余由模型词表容量补齐。BOS 不自动添加，EOS/PAD 与源 tokenizer 一致。
- 全新工具准备命令实际成功后，用其产出的 CPU 量化器再导出，GGUF SHA256 与先前真实加载的文件完全相同；两份来源身份也相同。临时验证输出不是永久发布路径。
- llama.cpp `llama-completion` 实际以原始 Alpaca 提示、温度 0、生成上限 8 token 加载并生成，进程退出 0，用时 4.00 秒。HF tokenizer 与实际运行记录都为 22 个输入 token；此数量一致不证明全词表映射逐项一致。
- LM Studio 0.4.25+1、GGUF 引擎 2.46.0 实际复制导入、加载并生成，加载 10.81 秒、生成 0.42 秒。该试验使用内嵌 Qwen3 聊天模板，与原始 Alpaca 试验分开记录，不混用分数。
- 只卸载本轮自己的模型标识并删除本轮导入副本，已有 3 个用户模型保留，最终加载模型为 0。本轮验证后公开接口从初始未运行变为运行，已停止并核对恢复未运行。导出模型与证据保留在临时目录。
- 首次 LM Studio 操作遇到 CLI key 契约差异：完整文件路径不能作为 `lms load` 的 key；改用实际 `lms ls --json` 中唯一匹配的 `modelKey` 后成功，使用文档已修正。两次失败尝试的本轮副本也已清理。

加载步骤依据官方 [导入命令](https://lmstudio.ai/docs/cli/local-models/import) 与 [加载命令](https://lmstudio.ai/docs/cli/local-models/load)，同时以本机实际返回为准。
