# 业务对照评测与坏例证据

对照评测使用当前已确认数据版本的同一开发集，依次加载基座和微调模型，使用相同提示、生成设置和业务评分规则。训练与评测共用 `render_alpaca_prompt`，评测提示的答案部分为空。独立测试集不参与这个迭代比较过程。

内置提供三种处理方式：

- 已确认的单字段分类：完整输出精确匹配，可显式选择是否忽略首尾空白。
- 结构化答案：比较明确指定的 JSON 字段，保留类型区别，拒绝重复键与非有限数值。
- 开放任务：保存输出供业务核对；缺少可执行业务规则时不生成质量达标结论，也不套用分类准确率。

另有可确认的自定义业务规则：用户说明可执行的判断标准，Agent 结合真实开发题起草规则，经过正例、同题错误输出反例和隔离重放验证后，展示实际分数与理由供用户确认。例如金额提取可以允许货币符号、限定金额误差，并给予部分分数；不能只用字符串精确匹配判断这类业务。

“是否专业”“回答是否好”这类尚未明确的要求，需要继续补充业务标准。程序不会把临时关键词规则当成主观质量判断，也不自动确认 Agent 起草的评分器。

自定义代码沿用现有操作系统隔离，只接收题目输入、参考答案和实际输出，并返回每题的 `score`（0 到 1）和理由。原行、输入和答案必须保留；未通过验证、丢行或非法分数都不能采用。相同规则下分别展示业务平均分与通过率，单题通过门槛来自确认的规则，最终验收的最低通过率由用户另行指定。部分得分不自动表示通过，失败和截断按零分保留在全部题目分母中。

规则、配置、正反例与任务含义一起保存；改变目标、输入或答案含义需重新验证确认。同一任务增加训练资料时可复用仍适用的规则。对照报告保存完整规则身份，改了评分规则后需统一重评，不能把不同规则的分数差称作模型改善。样例验证只证明已检查的行为，不证明规则覆盖所有业务情况。

生成失败、模型加载失败和截断行仍进入总分母，并单独报告有效覆盖率。输出达到长度上限且未正常结束时标记截断，保留完整内容，不截取第一行标签来提高准确率。模型释放失败会停止继续加载下一个模型。

## 结果身份

报告保存数据版本、开发集内容摘要、提示摘要、评分与生成协议，以及实际模型权重和配置文件的内容摘要。同一对照运行再次使用基座前会重新核验文件内容；如果文件已变化，后续模型记录为失败，不沿用缓存身份继续比较。

`BusinessEvaluationService` 提供同步 `compare`、按 ID 读取的 `get_report` 和可按数据版本或套件 ID 筛选的 `list_reports`。报告逐模型保存为 JSON。`completed` 表示评测执行完成，不表示业务目标已达成；`completed_with_failures` 保留具体失败行。无套件时必须使用同一数据版本；固定套件模式允许训练数据改变，但评分题、实际提示、答案和评分协议必须一致。

```python
from src.workbench.business_evaluation import (
    BusinessEvaluationService, EvaluationModel, EvaluationProtocol,
)

report = BusinessEvaluationService("outputs/workbench/evaluations").compare(
    confirmed_session,
    [EvaluationModel("基座", base_model_path),
     EvaluationModel("本轮微调", base_model_path, adapter_path=adapter_path)],
    EvaluationProtocol("classification_exact", max_new_tokens=256),
)
```

## 给 Agent 的坏例证据

`EvaluationDiagnostics(report, session)` 要求使用报告对应的确认任务快照。它重新验证数据与协议摘要、实际开发集，以及每条评测记录的来源、期望和提示。不能把旧数据版本的报告附到新任务，不能删掉失败行，也不能把独立测试集改名后用于迭代诊断。

```python
from src.workbench.evaluation_diagnostics import EvaluationDiagnostics

evidence = EvaluationDiagnostics(report, confirmed_session)
summary = evidence.summary()
page = evidence.read_cases(model="本轮微调", offset=0, limit=20)
```

摘要按模型完整统计正确、答案不匹配、截断、生成失败、无效输出、评分失败与待业务核对。`bad_case_count` 表示所有模型的需核查记录总数，包括开放任务待审；`error_count` 单独排除这些尚无评分规则的待审记录。同一开发样本在两个模型上失败会计为两个模型证据，不能当作两个独立数据样本。

每条证据有稳定的 `evidence_id`（模型名称与评测行索引），保留原始文件及行号、处理后记录、目标、当前处理方案、标准答案、完整模型输出和实际错误。分页返回 `total`、`next_offset`、`has_more`，不会只取前几个错误就伪称覆盖全部问题。

单条证据超过页容量时，返回明确的 `content_status="requires_chunks"`。调用 `read_case_content(evidence_id, offset, limit)` 连续读取完整 JSON 内容；返回字段为 `content`、`total_characters`、`next_offset` 和 `has_more`。大文本不会被悄悄裁掉。

摘要中的事实来自确定性统计。可能原因明确标为待验证：例如触及长度上限可能涉及重复生成、停止标记、训练提示或实际输出长度，不能直接断言“再加长度”或“再训练几轮”就会解决。证据模块不调用 LLM、不修改业务目标或标签，也不自行启动下一轮训练。

`training_evidence()` 从被评测 adapter 的实际内容身份反查工作台训练回执，核对数据版本、配置与产物清单后提供训练配置、指标、监督预检汇总和 MLflow 关联。它不发送训练集或独立测试集原文。非工作台 adapter 缺少回执时明确 `not_available`，文件被修改或关联不匹配时返回 `invalid`，不会把另一次训练的配置冒充本次证据；旧记录缺少基础权重内容哈希时明确标为未核验。

结果解读 Agent 必须先读取评测摘要、有问题的实际行，以及微调对象对应的训练证据，再提交观察、待验证假设和下一步。超过单页容量的证据需连续分块读完后才能引用。页面操作和 CLI `eval-analyze` 共用这条流程，解读单独持久化，不自动改变数据、目标或训练方案。

## 固定评测与第二轮改进

`EvalSuiteService.freeze(session)` 从已确认分区冻结开发题和最终测试题。后续 `materialize_dataset(..., evaluation_suite=ref)` 按原题的业务内容和分组匹配，不依赖重新上传后的行号。新增独立对象可以进入训练；与开发或测试对象关联的新增记录仍保留在对应分区，但不自动扩充评分题或分母。原题缺失、答案或指令改变、业务对象跨开发/测试集连接时会阻断，需建立新套件并统一重评。

报告同时保存实际训练数据版本和固定评分身份。历史模型的训练证据从自身 `run/session.json` 读取，并验证它没有训练过该套件的留出对象。诊断仍必须使用报告对应的数据快照，不能把旧报告与新来源行混搭。

`IterationService` 将真实父轮模型及评测、可检验假设、具体修改、业务期望、固定套件与新训练关联。用户确认提案后，修改数据继续经过全量预览确认；用本轮套件物化，然后准备和启动训练。参数继承父轮并显示覆盖项，当前从同一基座重新微调；尚不支持在父 adapter 上继续训练或检查点续跑。启动时获准的一次 OOM 恢复会关联到同一业务轮次，使用实际成功子运行参加评测。

第二轮结果在同一报告中比较基座、父轮和新模型，再记录采用、继续、停止或证据不足及理由。系统检查实际模型内容身份，不把重复点击训练当作有依据的改进。多项变化同时发生时，不能由分数变化证明某一项的因果作用。

确认包含数据修改的方向后，可调用 `revise_data_for_iteration` 或页面对应按钮。Agent 先读历史报告匹配的数据快照和真实开发坏例，再用已有数据工具执行新方案与预览，保存前后差异。旧确认失效，用户需查看新的实际输入/答案；模型的错误输出不能直接当作监督标签。新预览有业务歧义时停在问题说明，固定套件检查仍在后续物化时执行。

## 最终业务验收

开发对照用于定位问题，`AcceptanceService` 用固定测试题检验一个已选定模型。用户先明确业务标准、最低通过率和最低题数；服务冻结模型内容、题集、生成与评分协议，再显式执行。标准没有默认门槛。分类和 JSON 任务采用既定精确规则；开放任务逐题记录接受/拒绝及理由。失败与截断保留在分母，不能人工覆盖成通过。

结论区分 `passed`、`failed`、`insufficient_evidence` 和待人工核查。少量题全部答对也不能代替充足证据。重复点击同一次验收不重新生成；已经揭示的题目不能通过更换模型或套件标识重新作为首次独立验收。该记录只约束本地工作台保存的操作，不能证明用户从未在其他地方看过资料。

验收复用训练证据核验，检查实际 adapter 的工作台回执及训练分区与留出题的关系。未知来源的 adapter 可生成结果，但不能因此取得独立验收通过结论；记录为证据不足并保留观察到的数值。该核验不声称审计过基础模型的外部预训练语料。

`BusinessEvaluationService.evaluate_final` 提供底层单模型测试执行，交付判断应使用上述验收服务。默认 `list_reports` 只返回开发报告，最终报告需显式指定 `purpose="final_acceptance"`。最终题、输出与坏例只向用户展示；开发对照、诊断、Agent 分析及迭代入口均拒绝将最终报告用于改进。操作说明见[最终验收入口](agent-setup.md)。

## 当前范围

当前能够跨训练数据版本使用固定开发套件比较模型、读取坏例并关联改进轮次，并对选定模型执行单独的最终验收。Agent 可推荐本地 SFT/LoRA 方案，按确认方向重新执行数据工具形成预览，也可起草经隔离验证、待用户确认的可执行业务评分规则。任意业务修改的有效性、已支持 OOM 以外的技术故障自动修复和真实用户目标达成仍需实际业务验收。首个美股财报预测试点已接入时间策略、标签窗口、排除清单和对应固定题集检查；真实行情、Agent 数据理解与金融业务效果另行验证，不能由软件分区检查通过推断预测有效。

协议与证据回归测试使用可控运行器，验证流程约束，不代表真实模型质量。实际模型对照需要保留真实报告；即使模型成功加载、训练和生成，也可能在业务匹配上没有改善。
